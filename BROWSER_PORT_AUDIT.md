# Browser-port dependency audit

Scope: shipped application code and its Electron build/runtime entry points. Test fixtures and developer-only scripts are summarized separately. This report records the pre-migration audit; the Web Serial transport added after PoC approval is documented below.

## Executive summary

The MSP protocol/message layer is already transport-independent: `js/msp/` and `js/serial_queue.js` do not import Node or Electron APIs. The desktop boundary is `js/connection/connectionSerial.js` → `window.electronAPI` → `js/main/preload.js` → `js/main/serial.js`. A Web Serial transport can preserve the existing `ConnectionSerial` public contract (`connectImplementation`, `disconnectImplementation`, `sendImplementation`, callback registration, and `getDevices`) while removing only the IPC/native backend.

The browser target must run in a secure context (HTTPS or `localhost`). Web Serial and WebUSB require a user gesture for their chooser and are Chromium-family APIs, so unsupported browsers need a clear capability message.

## Safe implementation boundary after PoC approval

1. Keep `js/msp/` and `js/serial_queue.js` untouched.
2. Add a Web Serial implementation that preserves the `ConnectionSerial` public behavior: byte-array send, receive callback delivery, error callback delivery, connect/disconnect callbacks, and connection ID semantics.
3. Select desktop vs browser transports at one import/entry-point boundary; do not rewrite callers.
4. Build and run after this isolated serial step. Only after real-hardware serial confirmation, evaluate files, TCP/UDP, and DFU independently.

## Serial migration status

The validated initial serial increment is now in place:

- `js/connection/connectionWebSerial.js` implements the established connection contract using Web Serial, including a persistent read loop that recovers from transient (non-fatal) stream errors, a single persistent writer held for the connection lifetime, disconnect-event handling, and byte-array callback delivery.
- `js/connection/connectionSerialTransport.js` selects the browser or Electron transport at the import boundary.
- `js/connection/connectionFactory.js`, `js/port_handler.js`, `js/protocols/stm32.js`, and `tabs/firmware_flasher_restore.js` import that selector without changing their call sites or the MSP layer.

The browser build now has a minimal platform-services shim in `js/browser/platform.js` and a separate Vite configuration in `vite.web.config.js`. It persists small preferences in `localStorage`, uses browser file selection/downloads for basic import/export, and explicitly reports TCP, UDP, and local SITL as unsupported. `js/browser-entry.js` installs that shim only outside Electron before starting the existing renderer.

### CLI over Web Serial

Bringing the CLI tab up over Web Serial required three transport-adjacent fixes in `tabs/cli.js` (the MSP command layer itself is untouched):

- MSP requests are echoed back verbatim by the FC while it is in CLI mode, so the CLI now filters out complete, checksum-valid MSP v1/v2 frames (with cross-read buffering) before treating bytes as CLI text.
- The MSP queue is locked on CLI entry and unlocked on cleanup so pollers/retries cannot transmit during a CLI session.
- Disconnecting from an active CLI session now sends `exit` so the FC returns to MSP mode; without it the next connection's MSP requests were echoed, never answered.

A related infinite-retry bug in the auto-complete cache builder (`js/CliAutoComplete.js`) was also fixed.

Run `npm run web:dev` for a localhost development server, `npm run web:build` for the static `dist-web/` output, or `npm run web:preview` to serve that build locally. Full-configurator hardware validation through the new transport is the next gate; files, TCP/UDP, SITL, and DFU remain separate work items.
